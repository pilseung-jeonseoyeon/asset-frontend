# 백엔드에 요청할 항목 (프론트 연동 중 확인된 것)

최초 작성: 2026-08-09 · **갱신: 2026-08-09 (API-SPEC 전면 개정본 반영)**

확인 방법:
- `secret/API-SPEC.md` 2026-08-09 개정본(인증 §16, 대시보드 §4, 목표 §5, SSE §9.1, 부록 "응답 타입
  총람" 포함)과 1:1 대조
- 실행 중인 `http://localhost:8080`의 `GET /v3/api-docs`(OpenAPI)로 엔드포인트 51개와 응답 DTO
  필드명 대조
- 로컬 DB 직접 조회(시드 데이터 확인)

> **이 문서는 "아직 못 받은 것"만 남깁니다.** 이전 판 20개 항목 중 스펙 개정으로 해소된 것은
> 본문에서 지우고 맨 아래 "해소된 항목"에 근거만 남겼습니다.
>
> "못 그리는 것"은 응답에 값이 없어서 화면에 **아예 렌더하지 않은** 항목입니다 — 가짜 값을
> 채워 넣지 않았습니다.
>
> 우선순위: 🔴 막힘/배포 차단 · 🟠 화면 요소 누락 · 🟡 확인/규약

## 🔴 1. 배포 환경의 CORS 오리진과 refresh 쿠키 속성 (배포 차단 항목)

스펙 §16이 refresh 토큰을 `refresh_token` httpOnly 쿠키(`Path=/api/v1/auth`)로 확정했지만,
**배포 환경에서 이 쿠키가 실제로 붙을지는 아직 알 수 없습니다.**

프론트는 Vercel, API는 EC2로 **서로 다른 오리진**이 됩니다. 이때 쿠키가 `SameSite=Lax`(스프링
기본값)면 크로스 사이트 요청에 아예 실려 가지 않아 **새로고침할 때마다 로그아웃**됩니다.
로컬(`localhost:5173` → `localhost:8080`)에서는 같은 사이트로 취급돼 문제가 드러나지 않습니다.

**요청**
1. 배포 환경 CORS 허용 오리진 목록(Vercel 도메인 + 프리뷰 도메인).
   `Access-Control-Allow-Credentials: true`도 함께 필요합니다.
2. refresh 쿠키의 `SameSite` / `Secure` / `Domain` 값. 크로스 오리진이면 `SameSite=None; Secure`여야 합니다.
3. 위 값이 로컬과 배포에서 각각 무엇인지(프로파일별로 다르면 그 기준).

## 🔴 2. `AccountRes`에 `institutionId` / `interestRate` / `openedAt`이 없다

`GET /accounts`·`/accounts/{id}` 모두 `institutionName`만 주고 id를 주지 않습니다(부록 C의
`AccountRes`). `interestRate`·`openedAt`은 **등록 요청에는 있는데 응답에는 없습니다.**

**영향**
- 계좌 수정 화면이 기관을 **이름으로 역조인**해 id를 복원합니다
  (`src/screens/Assets/modals/EditAccountModal.tsx`). 기관명이 DB 유니크라 동작은 하지만, 기관
  목록 로딩이 늦으면 표시가 틀리고 동명 기관이 생기면 바로 깨집니다.
- `interestRate`는 **현재 값을 알 방법이 없어 수정 폼에서 아예 뺐습니다.** 모르는 값을 덮어쓰게
  하는 편이 더 위험해서입니다. 즉 **지금은 금리를 한 번 등록하면 수정할 수 없습니다.**

**요청**: `AccountRes`에 `institutionId`, `interestRate`, `openedAt` 추가.

## 🔴 3. 계좌의 `institutionId` · `maturityDate`를 해제할 수 없다

§1.4가 "`null`은 미변경"이라고 확정했습니다. 그래서 한 번 지정한 기관을 "미지정"으로, 한 번 넣은
만기일을 "만기 없음"으로 되돌릴 방법이 **없습니다**(계좌를 해지하고 새로 만드는 수밖에).

**요청**: 두 필드를 `null` 전송으로 해제할 수 있게 하거나, 해제 방법을 알려주세요.

## 🟠 4. 보유 종목 응답에 `ticker`와 현재가가 없다

`HoldingRes`는 `stockId`/`stockName`/`market`/`sector`/수량/평단/평가액/손익뿐입니다(부록 C).

**못 그리는 것**: 종목 카드의 "현재가 / 전일대비" 컬럼 — 아예 렌더하지 않았습니다.
티커는 `GET /stocks` 전체 목록을 따로 받아 `stockId`로 조인해 채우고, 실패하면 빈 값으로 둡니다
(종목 수가 늘면 전체 목록을 매번 받는 비용도 커집니다).

**요청**: `ticker`, `currentPrice`, `previousClose` 추가. 계좌별 보유 조회가 가능한지도 확인이
필요합니다(여러 증권 계좌에 같은 종목이 있을 때 합산되는지).

## 🟠 5. 보유 종목에 원가(`principalKrw`)가 없다 — 청산 종목에는 있는데 비대칭

**못 그리는 것**: 주식 화면 상단 "총 매수금액"의 정확한 값.

현재는 `총평가금액 − 평가손익`으로 역산합니다. §10.6 **청산** 종목에는 `principalKrw`(수수료 포함
원가)가 있는데 **보유 중인 종목에는 없어서** 같은 화면 안에서 원가의 정의가 갈립니다.

**요청**: `GET /stocks/holdings/summary` 신설, 또는 `holdings[]`에 `principalKrw` 추가.
겸사겸사 `unrealizedPnlKrw`가 `평가액 − 원가(수수료 포함)`가 맞는지도 확정해 주세요.

## 🟠 6. `exchanges/summary`에 원화 환산액·현재 환율이 없다

`FxSummaryRes`는 `heldForeignAmount`, `weightedAvgRate`, `unrealizedGainKrw`, `realizedGainKrw`뿐입니다.

**현재 처리**: `/indices`의 `USDKRW.currentValue`를 곱해 원화 환산액을 **프론트에서 계산**하고
"현재 환율 기준"이라고 밝혀 표기했습니다. 다만 이 환율은 한국수출입은행 값이고, 서버가
`unrealizedGainKrw`를 계산할 때 쓴 내부 환율과 소스가 달라 **소수점 단위로 어긋날 수 있습니다.**

**요청**: `heldValueKrw` 또는 `currentRate`를 응답에 넣어 주세요(서버 기준값으로 통일하기 위함).

## 🟠 7. `/assets/distribution`의 계좌 항목에 기관 정보가 없다

`AccountContribution`이 `{accountId, accountName, valueKrw}`뿐입니다(부록 C).

**영향**: 자산 카테고리 모달의 계좌 행 둘째 줄(기관명)을 채우려고 `GET /accounts`를 **한 번 더**
받아 조인합니다. 해지 계좌는 목록에서 빠지므로(§1.5 소프트 삭제) 그 계좌가 섞이면 조인이 깨져
기관명이 빈칸이 됩니다.

**요청**: `AccountContribution`에 `institutionName`(또는 `institutionId`) 추가.

## 🟠 8. `AccountRes`에 원금(초기 투자금)이 없다

계좌 상세 모달(`AccountDetailModal`)에서 "현재 잔액"은 `balance`로 그릴 수 있지만, 그 옆에 함께
보여주던 "원금 대비 +N%" 배지를 그릴 근거가 없습니다. `CreateAccountReq.initialBalance`는 생성
요청에만 있고, 이후 응답 어디에도 원금(또는 누적 입출금 기준 원가)이 내려오지 않습니다.

**못 그리는 것**: 계좌 상세의 원금 대비 증감 배지 — 배지 자체를 제거했습니다.

**요청**: `AccountRes`에 원금 필드(예: `initialBalance` 또는 원가 재계산치)를 추가하거나, 스냅샷
원장에서 서버가 계산한 손익률을 별도 필드로 내려주세요. (2번과 함께 처리하면 좋습니다.)

## 🟠 11. 기관 `icon` / `color`를 제거할 수 없다

§2.3의 PATCH는 "값을 넘긴 필드만 수정"이라 `null`이 "미변경"으로 처리됩니다. 실제 서버로도 `icon`
키를 생략하든 `icon: null`을 명시하든 기존 아이콘이 그대로 유지되는 것을 확인했습니다.

**현재 처리**: 이미 아이콘이 있는 기관을 수정할 때 "선택 안 함" 버튼을 잠그고 "아이콘 제거는 아직
지원되지 않아요"라고 안내합니다.

**요청**: `icon`/`color`를 `null`로 보내 제거할 수 있게 해 주세요.

> 허용 값 집합 질문은 해소됐습니다(§2.2에서 `@Size(max=40)` 자유 문자열로 확정) — 프론트는
> `src/design/bank-institutions.ts`의 `tokenKey` 체계를 그대로 씁니다.
> **다만 서버에 이미 들어 있는 기관 32개의 `icon` 값이 이 체계와 다르면 브랜드 컬러가 전부
> 기본값으로 폴백됩니다.** 기존 데이터의 `icon` 값이 tokenKey와 같은 체계인지 확인해 주세요.

## 🟡 13. 정산월의 경계가 응답에 없고, 엔드포인트마다 기준이 다르다

**§6 앞머리가 이 문제를 직접 인정하고 있습니다**: `year`/`month`를 받는 API 중 **§6.5 일별 요약만
달력월**이고 나머지는 정산월입니다. `monthStartDay`가 1이 아닌 사용자는 같은 `year=2026&month=8`로도
API마다 다른 구간이 잡혀 **일별 합계의 합 ≠ 월 합계**가 됩니다.

**영향**
- 가계부 헤더의 기간 경계 표기("6월 4주차 (6.22–6.28)" 같은 라벨)를 **보류했습니다.** 말일 보정
  규칙(예: `monthStartDay=28`이고 2월)이 문서에 없어 서버와 어긋난 라벨을 만들 수 없어서입니다.
- 주간 탭은 서버 범위 조회가 없어(§6.5가 `year`/`month`만 받음) 월 데이터를 받아 프론트에서 잘라
  씁니다 — **한 주가 월 경계를 넘어가면 그 주를 온전히 그릴 수 없습니다.**

**요청**
1. 월 기준 응답에 `periodStart`/`periodEnd`를 동봉하거나, 정산월 경계 계산 규칙(말일 보정 포함)을
   문서화해 주세요.
2. `summaries/daily`에 `from`/`to` 파라미터를 허용해 주세요.
3. §6.5만 달력월인 것이 의도인지, 정산월로 통일할 계획이 있는지 알려주세요.

## 🟡 15. 단건 조회가 없다

## 🟡 19. 없는 기능

- **자산 배분 "목표 비율" API 부재** — §5 Goal은 금액 목표(목표 자산/시점/월평균 수입)라 별개입니다.
  `TargetRatioModal`은 **여는 버튼조차 없는 죽은 화면**임을 확인했습니다. 구현 계획이 없다면 화면
  제거 여부를 제품 결정으로 확정해 주세요.
- **종목 삭제 API 없음** — 등록/수정/검색만 있어 잘못 등록한 종목을 지울 수 없습니다.
- **CSV 가져오기 없음** — 엑셀 내보내기만 있습니다. 가계부 화면의 "CSV 가져오기" 버튼은 제거했고,
  설정 화면의 "엑셀 · CSV 가져오기" 항목은 아직 동작하지 않는 상태로 남아 있습니다.
- **거래 키워드 검색 없음** — `TransactionSearchReq`에 `description` 텍스트 검색 파라미터가 없습니다.
- **페이지네이션이 `/transactions`에만 있음** — `/trades`, `/exchanges`는 건수가 늘면 전량 반환됩니다.
  `/exchanges`는 `currency`가 필수라 "전 통화 환전 내역" 화면도 만들 수 없습니다.

자체가 불가능**합니다. 신규 가입자는 카테고리 설정에서 소분류를 직접 만들기 전까지 가계부를 아예
쓸 수 없습니다.

**요청**
1. 대분류별 기본 소분류 시드를 넣어 주세요(최소한 자주 쓰는 몇 개라도).
2. 신규 가입 시 `user_settings` 기본행이 자동 생성되는지 확인해 주세요. 안 된다면 미존재 시
   기본값(`monthStartDay=1`)으로 응답해 주세요 — 지금 프론트는 404 `USER_SETTINGS_NOT_FOUND`를
   기본값으로 폴백 처리해 두었고(`src/services/user/user.hook.ts`), 서버가 보장해 주면 이 폴백을
   걷어낼 수 있습니다.

## 🟡 22. `assetClassName`이 디자인 라벨과 다르다 — 표기는 프론트가 소유하도록 변경, 분류 기준 확인은 여전히 필요

`GET /assets/distribution`이 내려주는 `AssetClassGroup.assetClassName`이 원본 디자인 문구와
다릅니다. 예: `CASH_PENSION` → 서버 "현금·연금" / 디자인 "현금", `ETC` → 서버 "연금저축·기타" /
디자인 "연금·기타". **2026-08-15부터 화면은 서버 `assetClassName`을 더 이상 쓰지 않고, 항상
`ASSET_CLASS_META`(`src/data/assetsView.ts`)의 프론트 고정 라벨("현금", "연금·기타")로 표시하도록
바꿨습니다.**

다만 표기만 바꿨을 뿐, **서버의 실제 분류 기준(어떤 계좌 유형이 `CASH_PENSION`/`ETC` 중 어디에
집계되는지)은 여전히 확인되지 않았습니다.** `CASH_PENSION`이라는 enum 이름 자체가 "연금 계좌가
현금 버킷에 합산된다"는 뜻일 수 있는데, 이게 맞다면 화면 라벨을 "현금"으로 바꿔도 그 카드 금액에는
여전히 연금 자산이 섞여 있게 되어 제품 분류 의도(연금은 '연금·기타' 카드에 속해야 함)와 어긋납니다.

**요청**: 두 assetClass의 실제 분류 기준(어떤 `AccountType`이 어디에 집계되는지)을 확인해 주세요.
연금 계좌(`PENSION`/`PENSION_SAVINGS`)가 `CASH_PENSION`에 집계되고 있다면 `ETC`로 옮겨 주시거나,
프론트가 표시 단계에서 재분류할 수 있도록 계좌 유형별 집계 기준을 알려주세요.

## 🟡 23. 대시보드 summary만으로는 "계좌 없음"과 "총자산 0원"을 구분할 수 없다

`GET /dashboard/summary`(§4.1)에는 계좌 개수나 계좌 보유 여부 필드가 없어, 프론트는
`totalAssetKrw === 0`을 "신규 사용자(계좌 0개)"로 간주해 빈 상태 UI(계좌 추가 안내, 리포트 배너
숨김 등)를 그립니다(`src/data/dashboardView.ts`의 `isEmpty`). 하지만 계좌는 있는데 잔액을 전부
소진해 총자산이 정확히 0원인 사용자도 같은 조건에 걸려, "계좌를 추가하고 총자산을 한눈에
확인해보세요" 같은 계좌가 없다고 가정한 안내를 보게 됩니다.

**요청**: `GET /dashboard/summary` 응답에 `accountCount`(또는 `hasAccounts` boolean) 필드를
추가해 주세요. 추가되면 프론트 빈 상태 판정을 총자산 금액이 아니라 계좌 보유 여부 기준으로
바꾸겠습니다.
